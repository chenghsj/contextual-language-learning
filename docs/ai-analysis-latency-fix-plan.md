## 實作決策與範圍

本節將前次方向細化為可執行工作包。新任務採新流程，既有任務保留原 plan 與續跑路徑。完整教材時間與第一個完整場景的可讀時間分開驗收；只出現翻譯、空白閱讀器或生成中提示不算首場景交付。

主線保持目前使用者選擇的模型與思考強度；先驗證修正預算、減少輸出及場景並行的效果。低思考強度只作獨立對照實驗，不成為默認實作的隱含前提。影片全來源照常檢視，啟用類別、例句數與來源覆蓋不縮減。

### 延遲預算必須能算通

本案例正常路徑預算為 5 次候選掃描、1 次選材及 4 次完整場景教學，約 10 次；修補或必要的語義去重另計，不能隱藏在統計外。

候選與教學並行度皆先設 2。令 C 為單一候選呼叫時間、S 為選材時間、T 為場景教學時間、M 為合併和必要裁決時間，忽略排隊時：首場景約為 3C + S + T，全部約為 3C + S + 2T + M。這只是排程下界的估算，重試、限流及輸入差異必須另記。

例如 C=10 秒、S=10 秒、T=45 秒、M=30 秒時，首場景約 85 秒、全部約 160 秒，才支持目標。若 C 仍約 50 秒，首場景至少約 205 秒，不能宣稱 90 秒。因此先驗證小樣本的真實 C/S/T，再決定架構投入；不以增加輸出額度自行推算加速幅度。

### 並行、去重與失敗語意

- 每場景讀取不可變來源與設定，不讀取另一個尚未完成場景的可變陣列。場景 ID、來源與輸出預算在呼叫前保存；回應先驗證再落盤，保存後才發出可讀通知。
- 跨場景去重使用獨立的引用／等價索引，保留每個已發布 point/item 的原始 ID 與來源範圍。確定等價的內容共用閱讀呈現；不能只因字面相同就合併。真正需要語義判斷時，只裁決候選小組，不重生所有場景；耗時與用量計入 M。
- 全局整理不能刪除已被閱讀、收藏或播放引用的 ID；最終輸出及 reader/favorites 的解析都須理解該索引。若現有 V7 格式無法相容表達，使用明確的新格式版本與雙讀支援，不將新語意塞進舊格式冒充相容。
- 超大場景若無法一次完成，只在該場景內依完整單元切分；仍保留來源覆蓋、必要前後文與共享引用約束。首場景計時到整個場景完成，不把首批單位冒充完整場景。
- 候選、場景與裁決工作分別記錄 pending/running/validated/failed，以及已完成輸出、修補次數、擴額次數和付款呼叫。中斷後先恢復 checkpoint，不重設有界重試次數。
- 一個場景失敗不丟棄其他已驗證結果；任務維持未完成且可續跑。全域取消停止新請求，保留取消競態中已收到的有效輸出。明確 429 降低並行並遵守原有重試限制。

### 部分閱讀與相容性

新增獨立的部分結果 envelope，包含 jobId、revision、selectedSceneCount、readySceneIds、任務狀態、有效場景及其必要的 points/items。它不使用完整教材的 completed 語意，也不覆寫最終 document。透過顯式的能力協商與必要的 protocol 版本更新處理新舊 Host/Extension 組合。

進度通知只發 revision/ready IDs，內容以現有分塊傳輸方式按需取得，避免重送日益增大的整份教材。Extension controller 忽略舊 revision、處理重連與亂序，App/reader 允許已完成場景閱讀，保留選取、捲動與影片位置。新增場景不強迫切換正在閱讀的場景。首次打開取代盲目等待必須是清楚可理解的既有生成流程延伸。

最終合併需原子提交；提交後即使程序中斷，恢復也只完成狀態提交與後續已授權流程，不再請模型生成。雲端備份先維持完整教材完成後觸發，避免把局部快照誤當成完成教材同步。若允許預覽收藏，須以永久來源及 point/item ID 保存，並測試最終整理後仍能讀取。

## 問題與目標

基準為本機任務 `22403764-25a8-4311-a69c-a17dec650b69`：462 條字幕、4 場景，耗時 43 分 49 秒，76 次模型呼叫、32 次輸出截斷。詳見 `work/ai-analysis-latency-2026-11-02.md`。

已確認未指定 thinkingLevel 時，Pi SDK 使用 medium，但本專案初始預算使用 8192 tokens；同模型明確 medium 的現有預算則為 32768。候選分析截斷後拆半重做，教學生成依序執行，放大重做成本。

使用者已指出 30 分鐘仍不可接受，因此原先「只縮短約 30%」的目標作廢。本計畫改為減少模型必做工作、解除串行依賴並逐場景交付，保留完整教材需求。針對這份 462 條字幕、4 場景的代表性任務，先以「首個完整可讀場景 60–90 秒、全部教材 3–5 分鐘」作為設計及實驗目標；不是已驗證的速度保證，不外推至任意長度影片或 high/xhigh 設定。首個結果變快不能取代全部完成時間的改善。

提高輸出預算仍是必要修正，但無法單獨達成新目標：原任務的候選分析有 38 次、教學有 37 次模型呼叫，需要同時避免截斷重做、簡化選材輸出並改善教學排程。保留使用者明確選擇的模型、思考強度、教材內容需求及品質驗證。

## 新的流程與延遲預算

1. 完整檢視來源的候選階段只輸出精簡候選範圍、必要上下文 ID 與短評分依據；來源原文、時間與可由程式取得的欄位不要求模型重複輸出。不在每個未入選候選上建立完整教學單元、精細字元分組或長篇教學提示。完整教學單元與精確來源覆蓋移到入選場景的教學階段建立及驗證。保留所有 primary cues 的檢視要求，不能靠未告知的抽樣或忽略難句達標。
2. 場景選擇讀取精簡候選；限制候選資料重複與不必要敘述，不強制合併全片分析成一個過大請求。以正常路徑約 5 次候選呼叫、1 次選材、4 次場景教學作為本案例的呼叫數設計目標，取代 76 次。這不是對模型永不拆批的保證。
3. 教學以完整場景為工作單位，安排有界並行，先完成最早場景；每場景保留全部要求的翻譯、教學與例句。選擇並行度 2 或 4 前，先實測供應商限流與用量，遇明確 429 降低並行。大場景預先依完整來源單元及預估輸出切分，避免反覆付出截斷成本。
4. 完成一個場景且通過局部驗證後即保存並可閱讀；其餘場景繼續生成。這需要新增部分結果讀取與進度狀態，不能將未完成文件標示為完整教材。失敗、重試與取消不移除已可讀場景。
5. 「自動」的低推理設定可作選材實驗候選，但必須經品質對照才採用；明確 medium/high/xhigh 不覆寫。每階段有效設定與上限明確保存，不能用降低使用者指定品質或省略啟用內容達成時間目標。

延遲預算以端到端量測為準：先量精簡候選與選材是否能在約 30–45 秒完成，再量單場景完整教學能否在約 30–60 秒完成。原任務單次呼叫中位數約 52–54 秒，因此若推理與輸出工作量未顯著下降，就不能聲稱 60–90 秒首場景已可達成。若小樣本無法達標，須回報階段瓶頸與品質／成本取捨，不藉由只展示進度動畫或部分翻譯宣稱成功。

## 第一階段：統一實際思考設定與預算

1. 在 Host 的模型解析邊界建立唯一的有效思考強度解析邏輯，依模型支援能力解析「自動」。目前支援 medium 的模型維持既有 medium 語意；不支援的模型使用 SDK 相同的能力對應規則，不向供應商傳送不支援的值。
2. 明確選取的強度必須保留；不支援的明確選項維持可理解的錯誤，不靜默降級。
3. 預估、新任務建立、候選分析、選材、教學生成與實際 createAgentSession 使用同一個解析結果。主要落點：`agents/pi.ts`、`jobs/manager.ts`、`generation/input-estimate.ts`、`generation/learning-execution.ts`、`generation/learning-points-prompts.ts`。
4. 將有效強度及預算策略版本保存到 execution，避免續跑或 SDK 升級改變同一任務的執行設定；保留 request 原始選項與 inputFingerprint，不直接改寫原始 request。
5. Gemini 3.8 Flash 的有效 medium 使用現有 32768 初始預算規則，並保留模型最大輸出、contextWindow/4、輸入安全空間與 pointsPromptFits 等限制。

第一批測試先重現：省略強度與明確 medium，在同一支援模型上應取得相同有效強度、預算與實際 session 參數。再涵蓋 low/high、非推理模型、小 context 或輸出容量、輸入預估與實際執行的一致性。使用真實 pipeline 的 generateText 測試接縫檢查傳出參數，不能僅測預算函式。

## 第二階段：相容性與續跑

- 新增 execution 欄位採相容讀取；舊教材不重寫，歷史 calls 不補造當時未記錄的有效強度。
- 舊未完成任務在使用者明確續跑時，記錄本次採用的預算策略及有效強度；不宣稱能從缺失資料精確還原歷史設定。
- 完成的候選、選材、教學及 pendingTeaching 一律沿用，不重新付費；保留過往 paid calls 與每批已保存的更高預算，不因新策略將其降低。
- 測試：取消與恢復、已收到有效輸出的競態、已完成教材讀取、舊 checkpoint、輸入指紋檢查及模型容量檢查。
- 若新增策略欄位可完整表達這次執行變更，不為純預算修正任意變更教學 prompt 或丟棄原有批次。

## 第三階段：解除教學依賴，再量測截斷策略

先以第一階段修正重測，再決定是否需要額外策略。避免同時提高額度、改 prompt、改拆批與增加並行，使結果無法歸因。

若修正後仍頻繁截斷，再實作有界的擴額策略：僅對已確認 length/truncated_output、模型仍有容量且輸入仍放得下的呼叫，先允許一次增加預算，再沿用既有拆批或保存失敗機制。將嘗試次數與預算存入 checkpoint，防止重啟後重新獲得重試次數。模型要求 needs_split、輸入過大、一般驗證失敗或未知傳輸失敗，維持各自既有處理，不一律加額重送。

目前每批讀取前批的 existingPoints/existingReusableItems，不能直接用 Promise.all 取代串行迴圈。先定義場景內與跨場景的 ID、共用學習點及合併契約：各場景使用獨立 namespace；場景內去重由該次教學負責；跨場景採穩定 registry 與明確別名對應，只有同義同用法才共用，不因字面相同合併不同語義。程式能驗證來源、引用與精確重複，但不能假裝能判定所有語義等價；確有歧義時需對小組候選定向裁決，其成本計入全部完成時間。逐步發布後的 ID 必須保持可解析，不能因稍後合併讓已讀場景或收藏失效。

先用一個固定 fixture 驗證跨場景同義重複、同形異義、取消、並行錯誤及重啟恢復，再啟用並行度 2；量測仍不滿足延遲預算時才評估 4。候選階段先維持並行度 2。所有新排程保持全域取消與付費呼叫記錄。

精簡候選契約、單元建立位置、並行合併與部分結果交付屬流程變更，應更新相應 workflow/prompt/策略版本；不能將新流程冒充舊執行。舊任務沿原有 plan 續跑，或由使用者建立新流程任務，不能靜默丟棄既有付費結果重規劃。

## 第四階段：驗收與交付

離線驗證包括上述測試、相關 Host/Core 型別檢查、Host production bundle 與 stdio smoke。檢查新增欄位可隨教材保存及讀回。只執行與改動相關的測試，再依共用 schema 影響範圍擴大檢查。

真實模型驗證分兩步：先以曾截斷的固定來源小片段驗證，再以相同 462 條字幕、模型及使用者教材設定建立新測試任務。保留原教材作為基準，不覆寫原任務。記錄有效強度、各階段實際等待時間、呼叫數、截斷數、拆批數、修補數及 input/output/reasoning tokens。

驗收條件：

- 設定正確性為硬條件：預估、checkpoint、session 實際強度及預算一致；保留顯式選擇及模型容量限制。
- 品質與恢復為硬條件：全部程式驗證通過、來源引用與教學要求完整、未破壞取消及續跑，並人工抽查翻譯和教學內容。
- 效能暫定目標：本案例首個完整可讀場景 60–90 秒、全部完成 3–5 分鐘，正常路徑約 10 次模型呼叫，截斷率低於 10%。原先 30 分鐘目標作廢。這是待驗證目標，不是速度保證；分別記錄首場景與全部完成時間，在資源允許時重複測量並報告中位數與範圍。
- 同時比較 token 用量；若速度提升卻大幅增加用量，需明列取捨，不能只報時間改善。
- 建置後安裝 Native Host，核對 bundle hash；重新連線後由實際擴充功能驗證，區分離線測試、真實模型與瀏覽器驗收。

交付順序：先修正有效設定與預算，再做一組精簡選材＋完整場景教學的真實延遲／品質實驗；達到階段預算後，才投入並行合併及逐場景閱讀整合。若實驗顯示模型本身單次耗時無法支持目標，應在擴大改造前回報證據及可選取捨。2026-11-02 已完成第一批程式與離線驗證，尚未發送真實模型請求或安裝新版 Host。
